# 5 分鐘面試口條與展示流程

> 對應簡報：`deliverables/IIoT_Communication_Fault_Diagnosis_Application_Deck_v2.pptx`  
> 使用方式：先以投影片說明研究脈絡，再視時間展示一個 Modbus 故障案例。數字與結果僅代表本專案已保存的受控或獨立實驗結果。

## 0. 面試前準備

- 填寫簡報封面的姓名與申請校系。
- 啟動 Docker Desktop，確認 PostgreSQL、Seq、相關 Simulator 與應用程式可連線。
- 準備一個已知的 Modbus 故障案例，例如 `NetworkDelay` 或 `ConnectionLost`。
- 先開好 Docker Desktop、Seq、資料庫查詢工具與應用程式畫面。
- 若現場網路、Docker 或 Simulator 無法啟動，改以 CSV 快照、實驗報告與投影片的保存結果說明，不宣稱現場重新執行成功。

## 1. 五分鐘時間配置

| 時間 | 投影片 | 目的 |
|---|---:|---|
| 0:00–0:30 | 1 | 說明研究主題與成果定位 |
| 0:30–1:00 | 2 | 說明現場問題與研究問題 |
| 1:00–1:40 | 3 | 說明系統如何建立可追溯證據 |
| 1:40–2:15 | 4 | 說明資料集與重現性設計 |
| 2:15–2:50 | 5 | 說明受控實驗的比較結果 |
| 2:50–3:50 | 6–8 | 說明泛化限制與 Unknown 安全設計 |
| 3:50–4:30 | 9 | 連結到研究所階段規劃 |
| 4:30–5:00 | 實機展示或結語 | 展示一個完整故障證據鏈 |

## 2. 逐頁口條

### 投影片 1｜研究主題（0:00–0:30）

「各位老師好，我的研究主題是工業物聯網通訊故障診斷。我自行建立一個可在 Windows 與 Docker 環境重複執行的平台，透過 Modbus TCP、OPC UA 與 MQTT 模擬工業設備通訊。研究不只比較規則、機器學習與 RAG 的診斷結果，也特別處理未知故障下可能出現的錯誤自動判斷。」

### 投影片 2｜研究動機與問題（0:30–1:00）

「製造現場的通訊異常可能來自延遲、斷線、認證、協定設定或資料格式問題。若只依賴人工閱讀日誌，很難累積跨協定、可比較的證據。因此我聚焦三件事：第一，如何保存一致的 Ground Truth；第二，比較 Rule、ML、RAG 的表現；第三，面對未知故障時如何避免模型過度自信。」

### 投影片 3｜系統架構（1:00–1:40）

「在系統設計上，我用 Simulator 產生 Modbus、OPC UA 與 MQTT 的正常和異常訊號，再由 Adapter 與 Collector 收集資料。每一個 Experiment Run 都保存實際故障類型、預測結果、錯誤碼與原始通訊內容。資料存入 PostgreSQL，日誌由 Seq 保存；診斷層則分成可追溯的 Rule、ML 模型與可引用知識來源的 RAG。」

### 投影片 4｜資料品質（1:40–2:15）

「目前正式受控資料有 15 種情境、1,500 次 Experiment Run、3,800 筆可診斷紀錄。我以 experiment_run_id 做資料切分，避免同一個 Run 同時落在訓練與測試資料。匯出 CSV 時保留覆蓋率與 SHA-256，讓資料來源可追溯。不過我也明確區分：受控資料的高分，只能是方法比較基準，不能直接當成真實產線的泛化結論。」

### 投影片 5｜受控評估（2:15–2:50）

「在受控資料上，Rule 與 RAG 都達到 100%，Logistic Regression 與 Random Forest 也達到 100%，SVM 則為 73.08%。這些結果顯示平台能完成可量測的比較，但我沒有停在這裡，因為真正重要的是未見條件下能否維持正確判斷。」

### 投影片 6｜G-01 / G-02（2:50–3:20）

「G-01 將 NetworkDelay 排除在原始訓練資料之外。結果三個 closed-set ML 模型都把它判成 None，0 / 398 正確。取得標註資料、重新訓練後，在 G-02 的獨立資料中，Random Forest 可達 388 / 388。這個實驗說明 ML 不會自動理解未見故障，模型能力必須用獨立資料驗證。」

### 投影片 7｜G-04 至 G-06（3:20–3:40）

「後續 G-04 到 G-06 再加入接近門檻的延遲、未映射的協定例外與 TCP reset。結果顯示不同模型、不同條件下的表現不一致。例如 G-06 中 SVM 的 Unknown 護欄為 0 / 100。這些負向結果是研究的一部分，幫助我界定方法邊界，而不是只挑選成功案例。」

### 投影片 8｜安全設計（3:40–3:50）

「因此我將低信心、Adapter 未映射例外與診斷證據衝突轉為 Unknown，再交由人工確認。人工可以回看 Ground Truth、原始請求和回應、錯誤碼、日誌與 RAG 知識來源。我將它定位為降低部分錯誤自動判斷的護欄，不宣稱可以全面解決未知故障。」

### 投影片 9｜申請與研究規劃（3:50–4:30）

「我希望以這套已完成的平台為研究所階段的基礎。接下來會擴增不同設備與網路背景的資料，驗證跨場域穩定性，也會研究 Unknown、拒答與成本敏感告警策略，以及 RAG 解釋品質與人工評閱方法。我期待將目前的工程實作，延伸成可靠、可解釋的工業通訊診斷研究。」

## 3. 30 秒實機展示腳本

> 只展示一種 Modbus 故障，不要在面試現場嘗試執行全部實驗。

「我現在以 Modbus 的 `NetworkDelay` 為例。Simulator 產生延遲後，Collector 會記錄請求、回應時間與 Adapter 觀測。這筆 Experiment Run 會保存 ActualFaultType。接著可以在 PostgreSQL 或 Seq 看到相同 Run 的錯誤與日誌；診斷層再輸出 Rule、ML 與 RAG 的結果。若信心不足或證據衝突，系統輸出 Unknown 並保留人工確認所需的原始資料。」

展示順序：

1. Docker Desktop：指出 Simulator、資料庫與日誌服務正在運作。
2. 觸發或選取一筆 Modbus `NetworkDelay` 實驗。
3. PostgreSQL：顯示 Experiment Run 的 ActualFaultType 與診斷欄位。
4. Seq：顯示同一時間範圍的日誌或錯誤碼。
5. 應用程式或輸出：指出 Rule、ML、RAG 與 Unknown 的差異。

## 4. 常見提問與回答

### 為什麼要同時使用 Rule、ML 和 RAG？

「三者的角色不同。Rule 可對應明確的錯誤條件並追溯原因；ML 可從標註資料學習分類；RAG 則提供知識來源與處置建議。研究的重點不是選出唯一最佳方法，而是比較它們在不同條件下的優勢與限制。」

### RAG 是否等同於診斷正確？

「不是。RAG 的價值在於提供可回查的知識來源與排查建議。它仍需依賴輸入證據與知識庫品質，因此我會把知識來源保存下來，並規劃加入人工評閱。」

### 為什麼不直接說模型正確率 100%？

「因為 100% 來自受控資料，可能反映訓練與測試條件相近。G-01 到 G-06 的獨立與未知情境顯示，模型在未見故障或接近門檻時可能失敗。因此我把泛化測試與失敗案例納入研究結論。」

### ML 的信心分數是什麼？

「信心分數是模型對目前分類結果的相對把握程度，通常由模型對各類別的預測機率或決策分數轉換而來。它不等同真實正確率，因此我會結合 Rule 證據、Adapter 狀態和人工確認，而不是只依賴一個分數。」

### 這個研究下一步可以如何擴充？

「我會加入不同設備、不同網路環境與更多協定例外資料，建立跨場域驗證。同時研究 Unknown、拒答及成本敏感告警，讓系統在不確定時能安全地交給人工。」

## 5. 結語句

「我的成果不只是建立一個故障分類器，而是建立一個能保存證據、重複實驗、比較不同診斷方法，並誠實呈現泛化限制的研究平台。我希望在研究所進一步把它發展成可解釋、可靠的工業通訊診斷方法。」
