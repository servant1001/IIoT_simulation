# 面試模擬問答與追問清單

> 使用方式：先用 30–45 秒回答每一題，再請朋友依「可能追問」加問。回答時以已完成實作與保存的實驗結果為主，不把規劃中的事項說成已驗證成果。

## 一、研究動機與定位

### 1. 為什麼選擇工業物聯網通訊故障診斷？

**回答重點**：工業現場的設備資料依賴穩定通訊，但異常可能跨網路、協定、認證與格式。人工查日誌成本高且難以複製。此專案將通訊模擬、資料蒐集、Ground Truth、診斷與實驗保存整合成可重現平台。

**可能追問**：這與一般 IT 網路監控有何不同？

**延伸回答**：IIoT 同時涉及設備協定語意與現場排查需求。除了連線是否成功，還須知道故障發生在哪個協定層、是否造成資料品質問題，以及如何提供可追溯的處置依據。

### 2. 你的研究問題是什麼？

**回答重點**：第一，如何將不同協定的故障保存為一致的 Ground Truth。第二，Rule、ML、RAG 在受控與獨立情境下各有何表現。第三，未知故障下如何避免模型產生過度自信的自動判斷。

**可能追問**：三個問題之間如何連結？

**延伸回答**：一致的 Ground Truth 是比較的基礎；比較結果能找出方法限制；Unknown 與人工確認則回應限制所帶來的安全風險。

### 3. 你認為專案最具研究價值的部分是什麼？

**回答重點**：不是單一受控資料的最高分，而是完整保存實驗證據，並透過 G-01 至 G-06 保留未見故障、接近門檻與協定例外下的成功與失敗結果，讓結論可被追溯與檢驗。

## 二、系統與資料設計

### 4. 為什麼選擇 Modbus TCP、OPC UA、MQTT？

**回答重點**：三者代表工業設備通訊中常見的不同型態。Modbus TCP 著重暫存器讀寫，OPC UA 具資訊模型與安全設定，MQTT 以發布訂閱與 Broker 為核心。跨協定設計可驗證資料模型與診斷流程是否能維持一致。

### 5. Ground Truth 如何產生與保存？

**回答重點**：每個 Experiment Run 在觸發情境時即記錄實際故障類型，並與 Adapter 觀測、錯誤碼、原始請求與回應、預測結果分開保存。這避免事後以模型輸出反推真實標籤。

**可能追問**：標籤是否會有誤？

**延伸回答**：模擬環境的優勢是可在故障注入時指定標籤，降低人工標註歧異；但也因此與真實設備資料不同，研究明確限制泛化主張。

### 6. 1,500 Runs、3,800 筆紀錄代表什麼？

**回答重點**：1,500 是正式受控情境的實驗執行次數，3,800 是可供診斷與分析的紀錄。資料涵蓋 15 種正常與異常通訊情境，並已匯出 CSV 快照與覆蓋率資訊。

### 7. 如何避免資料洩漏？

**回答重點**：以 experiment_run_id 為單位做 Run-aware split。同一個 Run 的多筆資料不會同時出現在訓練與測試，避免模型因重複訊號而得到過度樂觀的分數。

## 三、Rule、ML、RAG 的比較

### 8. 為什麼還需要 Rule-based，不能全部交給 ML？

**回答重點**：Rule 可直接對應已知錯誤與協定證據，容易追溯與修正。ML 對已標註模式有學習能力，但未見類別可能錯分。兩者是互補，而不是互相取代。

### 9. 你使用了哪些 ML 模型？為什麼？

**回答重點**：使用 Logistic Regression、Random Forest、SVM 作為可比較的分類基準。Logistic Regression 較易解讀，Random Forest 可處理非線性特徵，SVM 適合作為不同決策邊界的比較對象。

**可能追問**：為什麼沒有用深度學習？

**延伸回答**：目前資料量與研究問題適合先使用可快速驗證、可比較的傳統模型。深度學習需要更多跨設備、跨場域資料，這是研究所階段可延伸的方向。

### 10. RAG 在本研究中的角色是什麼？

**回答重點**：RAG 不取代 Ground Truth 或分類模型。它根據故障證據檢索知識文章，輸出可回查的可能原因與處置建議。重點是讓診斷建議具有來源，而非只提供一個無法解釋的類別名稱。

### 11. RAG 如何評估？

**回答重點**：目前以 Top-1、Top-3 與回應延遲評估受控資料，並保留知識來源。未來會建立人工評閱，以評估解釋是否正確、是否相關、是否對現場排查有幫助。

## 四、泛化、Unknown 與研究限制

### 12. G-01 的結果為什麼重要？

**回答重點**：將 NetworkDelay 完全排除於訓練資料後，三個 closed-set ML 模型都判成 None，0 / 398 正確。它直接證明模型無法自動辨識未見故障，不能只用受控測試的高分判斷系統可靠。

### 13. 重新訓練後 Random Forest 388 / 388，是否代表問題已解決？

**回答重點**：不代表。它只說明加入特定標註資料後，模型能在 G-02 的獨立資料正確判斷。G-04 接近門檻的延遲、G-05 協定例外與 G-06 連線中斷仍顯示模型與護欄有不同限制。

### 14. Unknown 是什麼？何時觸發？

**回答重點**：Unknown 是診斷系統承認不確定的輸出，不是忽略錯誤。低信心、Adapter 未映射例外或診斷證據衝突時，系統交由人工查看 Ground Truth、日誌、錯誤碼和原始通訊資料。

### 15. Unknown 是否可以完全防止誤判？

**回答重點**：不能。G-06 顯示不同模型下護欄效果不一致，SVM 為 0 / 100。因此 Unknown 是降低部分自動誤判的安全設計，不是全面保證。

### 16. 這個研究最大的限制是什麼？

**回答重點**：資料主要來自模擬器、單一設備設定和小型保留集。結果不能直接延伸成真實產線的全面泛化結論。後續必須納入不同設備、網路背景和現場資料。

## 五、工程實作與實務應用

### 17. 系統如何部署與執行？

**回答重點**：開發環境以 Windows、.NET 與 Docker Desktop 為主。Docker 提供 PostgreSQL、Seq、Mosquitto 與 Modbus Simulator 等服務；應用程式負責 Adapter、Collector、實驗與診斷流程。

### 18. 如果資料庫或 Docker 無法啟動，研究如何重現？

**回答重點**：正式資料已匯出 CSV 快照，保留覆蓋率與 SHA-256；實驗文件保存情境、結果與限制。即使現場服務暫時無法啟動，也能以保存資料與程式碼重建實驗條件。

### 19. 這套系統可以帶來什麼實務效益？

**回答重點**：它能把零散日誌轉成結構化的實驗與診斷證據，協助工程人員快速定位通訊問題。更重要的是，系統可在不確定時保留人工介入點，避免把錯誤分類直接變成自動處置。

## 六、研究所適配度與未來規劃

### 20. 進入研究所後，你最想完成什麼？

**回答重點**：建立跨設備與跨網路場域的資料集，驗證模型穩定性；研究成本敏感告警、Unknown 與拒答策略；建立 RAG 解釋品質與人工評閱架構，讓診斷能更符合現場排查工作。

### 21. 為什麼選擇本系所？

**回答重點模板**：

「我希望在【填入研究領域、實驗室或課程】的環境下，將目前的 IIoT 通訊故障診斷平台延伸為跨場域、可解釋且可驗證的研究。我的工程實作經驗能提供可重現的實驗基礎，也希望透過系所的研究方法與指導，提升資料分析與研究設計的嚴謹性。」

## 七、回答原則

- 先講結論，再用一項已保存的證據支持。
- 清楚區分「已完成的實驗結果」與「研究所階段規劃」。
- 被問到失敗結果時，主動說明它如何界定系統限制。
- 不確定的技術細節，說明會回到 Experiment Run、日誌與程式碼查證，不即興捏造數字。
